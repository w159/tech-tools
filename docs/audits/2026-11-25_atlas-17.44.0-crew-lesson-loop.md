# Atlas 17.44.0: the crew's self-improving loop (feedback-gated lessons)

Date: 2026-11-25. Model for every worker: claude-sonnet-5-5 at effort medium. Harness, fixture, raw results and
the store after the last run: `docs/audits/2026-11-25_atlas-17.44.0-crew-lesson-loop/`.

## What the video says, and what it does not

The request pointed at the YouTube short "Why Anthrophic Engineers stopped prompting" (Prinon Turio, 2026-11-21).
Its transcript describes a progression from agents to loops to graphs to "a system that literally improves
itself", and says 95% of Anthropic engineers run self-improving loops. It gives no mechanism and no source for the
figure. This audit does not repeat the figure as fact.

The mechanism came from public write-ups of the same idea:

- thenewstack.io "loop engineering": a separate grader verifies the work instead of the model that wrote it.
- noqta.tn, quoting Boris Cherny: mistakes are written into a shared CLAUDE.md so the next session avoids them.
- theagenticarchitect: a failing test's raw error output is fed back to the agent.

Atlas already had the first piece (independent checks judge each worker). What it lacked was the memory across
runs: a crew that failed a check on Monday made the same mistake on Tuesday.

## Design, against Atlas's tenets

Jerry's tenets for Atlas: the operating contract, honesty through models checked by adversaries, context moved
into tmux sessions, and decision models.

| Loop step | Atlas mechanism | Tenet |
|---|---|---|
| Capture | Only output that a deterministic check printed (`irc check`, the supervisor's global check). Pytest output is parsed with no model call: test id, the failing `>` line with two lines before it, the first `E` line. Secrets redacted, 360 chars. | Honesty: a lesson is evidence, never a model's claim. |
| Store | `<root>/.atlas/memory/lessons.json`, at most 300. | MEMORY.md and the lead's context are untouched. |
| Inject | A worker gets only the lessons whose test or file matches its `owns`/`tests` (the fix-round routing rule), fenced as untrusted recalled notes, at most 1,600 chars. No match adds 0 bytes. | Context stays in the tmux workers; the lead sees counts only. |
| Judge | After the verdict the checks score each shown lesson: passed -> win (proven); same failure -> repeat (kept, ranked first, says how many runs); new failure -> loss and new text; 2 losses or a deleted test file -> retired; a retired lesson that later fails a new way comes back. | The writer (worker) and the judge (the check) stay separate. |

Switch: `ATLAS_CREW_LEARN=off`. CLI: `atlas_lessons.py list`, `forget <id|test>`.

## Fixture

`fixture/`: six small modules (`kit.slug`, `money`, `dur`, `flags`, `ranges`, `table`) with a spec that leaves the
house conventions out (separator, rounding, units, boolean words, table layout). Workers see 13 weak visible tests;
the crew's global check also runs 43 hidden convention tests. Stubs pass 0 of 56, the reference passes 56 of 56.
This is the case the loop is for: the same task, or the same codebase, run again, where the first run can only
learn the conventions by failing.

A first version with readable tests (A0) was green on the first try with 75,767 tokens and proved nothing, so the
hidden suite was added.

## Results

Baseline = every run in which no lesson was shown (learning off, or an empty store). Learning = every run that
started from the previous run's store.

| Arm | Runs | Green | Worker tokens, mean (sd) | Range | Fix rounds |
|---|---|---|---|---|---|
| Baseline | A1-A4, L1, N1 | 2 of 6 | 524,828 (99,747) | 374,541 - 626,007 | 2 each; round 1 reran all 6 workers |
| Learning | L2-L5, N2-N5 | 8 of 8 | 136,181 (30,462) | 100,476 - 197,654 | 1 each; round 1 reran 1-4 workers |

Learning runs used 74% fewer worker tokens. The ranges do not overlap: the most expensive learning run (L2,
197,654) cost less than half of the cheapest baseline run (N1, 374,541).

Confirmation chain on the code that ships (N1 empty store, then each run seeded from the last):

| Run | Green | Tokens | Crew wall | Workers in fix round | Lessons |
|---|---|---|---|---|---|
| N1 | yes | 374,541 | 24.4 s | 6, then 2 | captured 20 |
| N2 | yes | 129,479 | 14.2 s | 2 | shown 20: 17 wins, 3 repeats |
| N3 | yes | 133,283 | 24.1 s | 2 | shown 21: 19 wins, 2 repeats |
| N4 | yes | 100,476 | 16.1 s | 1 | shown 23: 22 wins, 1 repeat |
| N5 | yes | 102,431 | 18.2 s | 1 | shown 23: 22 wins, 1 repeat |

Cost of the loop: round-0 worker prompts carried 6.1k to 6.7k chars of lessons in total across 6 workers. Capture
and scoring make no model call. On a fixture the crew passes on the first try (G1, 434 tests, learning on) the loop
added 0 bytes, wrote no file and no lock.

### Wall time is not claimed

Baseline runs A1-A4 and L1 took 129-135 s, learning runs 14-24 s, but most of that gap is a harness artifact: in
round 1 a baseline worker that could not read the hidden tests asked the lead on IRC and waited 100 s for an answer
(`irc wait` timeout); the benchmark runs the crew with no lead. With lessons the worker already had the failure text
and did not ask. N1, a baseline run without that stall, took 24.4 s. The token figures do not depend on the stall.

## Limits, stated plainly

- One synthetic fixture, n=6 and n=8, one model. Not a claim about real repositories.
- Lessons are keyed by test id. They help a repeated task or a codebase whose tests persist; they do not transfer a
  convention to a new test.
- A win is credited when a shown lesson's test passes, even if the worker would have passed without it. The
  baseline's round-0 failures (every worker, every run) make that unlikely here, but the judge cannot prove it.
- One note was never acted on: `test_flags.py::test_format` ("yes"/"no") failed the same way in N2-N5 with the
  note shown and marked as repeating. The fix round fixed it each time. The repeat counting keeps it (the earlier
  judge retired it after two such runs, which hid a true note); getting the worker to act on it is not solved.
- Earlier runs used earlier code: A1 and A2 ran with a 6,000-char shard tail (raised to 24,000 because it cut the
  detail of early failures and produced empty lessons); L1-L5 ran with the first judge (repeats counted as losses)
  and the first parser (a callee frame leaked into the lesson text). N1-N5 ran the shipped code. `results.json`
  holds every run.

## Reproduce

```bash
cd docs/audits/2026-11-25_atlas-17.44.0-crew-lesson-loop
./chain.sh   # N1..N5, learning on, each run seeded from the previous store
python3 bench.py --fixture fixture --plugin ../../../plugins/atlas --tag B1 --learn off   # one baseline run
```

Unit tests: `python3 -m pytest plugins/atlas/scripts/test_atlas_lessons.py -q` (15 tests; each of five seeded
faults in the judge, parser, revival, deleted-test and repeat-note code fails at least one).
