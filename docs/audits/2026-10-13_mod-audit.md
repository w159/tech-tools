## 3. Defects and weaknesses

### 3.1 The header the user asks about is replaced, not drawn

## 4. Open advisor note: does the sprite image renderer use terminal cell aspect, real glyphs, real colours?

Note: `t2b156948`, pending: "When SpriteReadable renders sprites to images for review, make it render at terminal cell aspect (each cell ≈1:2 wide:tall, half-blocks ▀▄ give 1:1 sub-pixels) with the real glyphs and colours".

Answer: no, and no renderer in the repo produces what the terminal draws.

- The only sprite-to-image code is `svg.ts` -> `sprites/grid.ts:105-120` `frameToSvg`: one `<rect>` per same-colour horizontal run, `width = len*scale`, `height = scale`. These are square pixels in SVG user units. There is no cell grid, no glyph, no text, no tile background. `squadSvg` draws it at scale 2 (`svg.ts:127`) on the legacy 4x4 `mini` frames (`contract.ts:114-120`, `grid.ts:23-27`).
- The terminal draws different art: `sprites/api.ts` `spriteRows` (`:363-370`) paints `ART[...]` from `sprites/art.ts` (hand-drawn 12x12 `m`, 16x16 `l`) or the procedural `paint` (`:221-238`), then `fold` (`:241-268`) emits `Run[]` with glyphs ` `, `▀`, `▄`, `█` and per-run `fg`/`bg` hex. `runs.ts:27` `fromSprite` adds the `#1b1f27` tile (`theme.ts:189`) behind fg-only cells. None of that data reaches `svg.ts`.
- Geometry: a square-pixel raster of the same pixel grid equals the half-block output when a cell is exactly 1:2, because each cell packs a top and bottom pixel (`api.ts:241-248`). So aspect is not the main gap. Missing are the real glyph rendering, the tile bg, the chip text (`api.ts:349-355`), the bubble (`:430-450`) and a real font cell ratio (not exactly 1:2 in practice). The renderer also reads the wrong art set.
- `grid.ts:44-90` `frameToRuns` is a second, different half-block fold (always `▀` with fg+bg, `▄` fg-only, no `█`: `:60-68`) from `api.ts:241-248`. Neither is wired to an image.
- The earlier PNG sheets (`/tmp/sprites-sheet.png`, `-m.png`, cited in advisor note `t71240751` evidence) came from an ad-hoc script; `/tmp/sprites-sheet*` does not exist now, `git grep` finds no script for it, and `/atlas-sprites` was removed (`docs/architecture/atlas-mod.md:5`). The note therefore stays open; a correct reviewer needs a renderer that consumes `spriteRows()` `Run[]` directly: draw each cell as a w x 2h box, fill `bg`/tile, then paint `▀▄█` as real half-cell rects in `fg`, ratio 1:2.

## What a good version needs (<= 5 bullets, no design)

1. Draw the contract header the output style defines (glyph, phase, n/m, state sentence) in one place and drop the other phase repetitions.
2. Show live activity independent of the lead's turn: worker state with tool, last line and age, animation driven by a clock that runs while any worker runs, failed or blocked workers sorted to the top.
3. Show lead-to-worker dispatch and the channel traffic in a compact stream, so orchestration is visible, without a 30-row pane over the transcript.
4. Size to the terminal: docked only when there is room, otherwise a few rows; no truncated current-phase labels; no emoji of uncertain width.
5. Review tooling and data trimmed to what is drawn: one sprite fold used by both the terminal and an image renderer at cell aspect, and the unread snapshot fields and tail reads removed or wired.
