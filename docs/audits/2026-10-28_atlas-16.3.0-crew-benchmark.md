# Atlas 16.3.0: crew benchmark and IRC evidence

Date: 2026-10-28. Question: can an Atlas tmux team that talks over IRC build a
multi-file deliverable in half the tokens and a quarter of the wall time of one
Claude prompt, on the same task and model?

Answer: tokens yes (36-47% of the single prompt), wall time no (36-37%; target
25%). Numbers below are measured, not rounded.

## Method

- Model `claude-sonnet-5-5`, effort `medium`, for the lead and every worker.
- Two fixtures, each a Python package with a SPEC.md, stub modules and a
  test suite. A reference implementation passes every test;
  the stubs pass none.
  - 8 modules (`pkgkit`: semver, ranges, manifest, registry, resolver, graph,
    lockfile, cli), 213 tests.
  - 18 modules (`pkgkit` plus `mdkit`, a markdown toolkit in a second package),
    469 tests.
- Each run starts from a fresh git copy of the fixture. Task text: implement
  every module per SPEC.md so `python3 -m pytest -q` passes, without touching
  the tests.
- Single arm: `claude -p "<task>" --model ... --effort medium --permission-mode acceptEdits --allowedTools Bash`.
- Crew arm: the same `claude -p` lead, with the same task plus six lines telling
  it to start `atlas_crew.py run --spec SPEC.md --files ... --tests ... --check 'python3 -m pytest -q' --wait 580`
  and not to read the spec itself.
- Tokens: input + cache writes + cache reads + output from `modelUsage` of each
  process's last `result` event, summed over the lead and every worker log. A
  process's `result` is cumulative, so only the last one per log counts (an
  earlier counter that summed every `result` line double-counted one single run
  at 4.59M; the corrected figure is 2.29M).
- Wall time: lead start to lead exit, measured outside the process.
- Pass check after each run: the full suite, then `git status --porcelain tests`
  (only `__pycache__` changes in every run below).
- Container: 4 CPUs, shared by every worker.

Cost is close to even: workers re-create their prompt cache, so cache writes
make up most of a worker's spend. The token target is on total tokens, and a
crew run spends roughly what one single run spends in dollars while finishing in
about a third of the time.

### The 16.2.0 team on the same task

The 16.2.0 `spawn-team` flow (planner, three implementers, verifier, each a full
default `claude` with every MCP server and the stock system prompt, worktree per
writer) used 8.67M tokens and 282 s: 10x the single prompt's tokens and twice
its time. The planner alone used 2.52M, one implementer 3.01M. It also ran every
worker under the lead's session id (fixed in 16.3.0, `scripts/test_atlas_mux_env.py`).

## Do workers really talk?

Yes. Two transcripts from the channel log (`irc/log.jsonl`), offsets from kickoff.

A human on a real IRC client (raw TCP to the gateway on 127.0.0.1, nick
`jerry`), on the final code. The gateway refused the nick `geom` with 433
because a worker held it.

```text
  1.1s jerry  -> #smoke2 [irc] geom, report: human on IRC here. Post the helper name you agreed on when you have it.
  2.8s report -> geom          report: what's the exact display-name helper in geom.py (name/signature)?
  4.4s geom   -> #smoke2       READY geom: geom.Circle(r), geom.Rect(w,h), .area(), geom.total_area(shapes), geom.shape_name(shape)->str
  6.3s geom   -> #smoke2       geom helper: geom.shape_name(shape) -> str (e.g. 'Circle', 'Rect'). Already in geom.py; tests pass.

 16.5s lead   -> #smoke2       Crew finished: global check exit 0.
```


In the six final benchmark runs the workers sent 0 direct messages and synced
through READY announcements (3 to 12 per run): with a precise spec section each,
nobody needed to ask. The channel carries traffic when there is a real
dependency question, as above, and costs nothing when there is not.

## How it works (code)

| Piece | File |
| --- | --- |
| Planner, tmux launcher, supervisor, reaper, fix rounds, summary | `plugins/atlas/scripts/atlas_crew.py` |
| Channel log, RFC 1459 gateway, `say`, `need`, `wait`, `stats` | `plugins/atlas/scripts/atlas_irc.py` |
| PostToolUse delivery, PreToolUse leases (incl. Bash writes), Stop check gate | `plugins/atlas/hooks/crew_worker.py` |
| Tests (29) | `plugins/atlas/scripts/test_atlas_crew.py` |

Why it is cheaper: the lead never reads the spec or the code; each worker carries
its own spec section and stub only; and the per-call floor is cut from 55,846
tokens (default `claude -p` here: MCP tool schemas, user settings, stock system
prompt) to 3,809 (`--strict-mcp-config`, project settings only, tools
`Bash,Edit`, a short replacement system prompt). That floor is paid on every
model call of every worker.

## Defects found by running it, and fixed

- Spec sections were cut at `#` lines inside code fences; headings are now found
  with CommonMark fence rules.
- A worker ran `cat > file` with no input; the Bash tool backgrounded it at 120 s
  and the process sat idle for 9 minutes after its result. Workers now run with
  `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, and the supervisor reaps a worker
  still alive 20 s after its result (counted as success when the result was).
- A worker waited on `--from lead` for a READY the lead never sends, then slept
  90 s. `irc need <peer>...` replaced that pattern, and `irc wait` refuses names
  that are not on the team.
- The lease hook only covered Edit/Write; a Bash redirect, `tee`, `sed -i`,
  `cp/mv` or Python `open(..., 'w')` on a peer's file is now denied too.
- Token counting summed cumulative `result` events (see Method).
- `atlas_mux.clean_env` leaked `CLAUDE_CODE_SESSION_ID` to workers.

Runs made on code with a defect were discarded and rerun; none of them are in
the tables.

## What did not reach the target, and why

Wall time is 36-37% of the single prompt's median, not 25%. The crew's own
wall time is 34-53 s; the rest is the lead (about 15 s: process start, two model
calls, exit). Inside the crew, the floor is the largest module's critical path
plus the CLI module, which imports every other module and so finishes last; four
CPUs are shared by up to 18 workers.

What would close it, in order of expected gain:

1. Start the crew without a lead model call (a `/atlas-crew` command or hook that
   runs `atlas_crew.py run` directly): removes most of the 15 s.
2. Split the largest modules across two workers by function, and give the CLI
   worker stub imports so it does not wait on peers.
3. More cores: with 18 workers on 4 CPUs, test runs inside workers queue.

A low-effort crew run (one valid run: 778k tokens, 63.2 s) was not faster; effort
is not the bottleneck.

## Reproduce

The harness (`arm2.sh`, `acct.py`) and fixtures lived in the session scratch
space; the commands it ran are the two arms under Method. Per-run `result.json`
files recorded tokens per process, wall time and pytest output.
