# Atlas 16.4.0: crew benchmark

Date: 2026-10-28. Question: after 16.3.0 (36-47% of the single prompt's tokens,
36-37% of its wall time), can the crew reach a quarter of the wall time of one
Claude prompt, on the same task and model?

Answer: tokens 13-16% of the single prompt (target 50%: met with room to spare).
Wall time 28-30% (target 25%): still missed, by 4.9 s on 8 modules and 9.6 s on
18 modules. Numbers below are measured, not rounded.

## Method

Same as the [16.3.0 page](2026-10-28_atlas-16.3.0-crew-benchmark.md), except the
crew arm.

- Model `claude-sonnet-5-5`, effort `medium`, for the lead and every worker.
- Two fixtures, each a Python package with a SPEC.md, stub modules and a test
  suite. A reference implementation passes every test; the stubs pass none.
  - 8 modules (`pkgkit`: semver, ranges, manifest, registry, resolver, graph,
    lockfile, cli), 213 tests.
  - 18 modules (`pkgkit` plus `mdkit`, a markdown toolkit in a second package),
    469 tests.
- Each run starts from a fresh git copy of the fixture. Task: implement every
  module per SPEC.md so `python3 -m pytest -q` passes, without touching the tests.
- Single arm: unchanged from 16.3.0. `claude -p "<task>" --model ... --effort medium --permission-mode acceptEdits --allowedTools Bash`.
  Its rows and medians below are copied from the 16.3.0 page, not rerun.
- Crew arm (new): `claude -p "/atlas:atlas-crew --spec SPEC.md --files '<glob>' --tests '<pattern>' --check 'python3 -m pytest -q' --model claude-sonnet-5-5 --effort medium" --plugin-dir <repo>/plugins/atlas`,
  with the same model, effort and permission flags as the single arm. The skill
  runs the crew as pre-executed shell before the lead's first model call.
- Tokens: input + cache writes + cache reads + output from `modelUsage` of each
  process's last `result` event, summed over the lead and every worker log.
- Wall time: lead start to lead exit, measured outside the process.
- Pass check after each run: the full suite, then `git status --porcelain tests`
  (only `__pycache__` entries changed in every run below).
- Container: 4 CPUs, shared by every worker.

## What changed since 16.3.0

- Skill entry: `/atlas:atlas-crew` pre-executes `atlas_crew.py run` before the
  lead's first model call. The lead is 1 turn and about 57k tokens (57,450 to
  58,404 in the six runs) instead of 2 turns and about 119k.
- Peer interfaces in each worker's context: the public skeleton of every planned
  file it imports, so a worker codes against peers without reading them or
  asking.
- `irc check` waits for the peers a worker imports and posts DONE itself, only
  when the unit check exits 0. Workers no longer announce READY.
- Early exit: after a Bash call whose check posted DONE, the PostToolUse hook
  re-runs the check and ends the session if it passes, so the worker spends no
  final model turn.
- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` on workers: no telemetry, flag
  fetch or summary round trip; `claude -p` exits about 3 s sooner after its
  result.
- Verified DONE (`irc check`), new-only `irc wait`, and a deny on `sleep N`
  (N >= 3 s). These came from a 91 s outlier: a worker piped its check through
  `tail`, so a failing check still exited 0 and posted a false DONE; a peer's
  `irc wait` matched that DONE from the log history and went on; the peer then
  slept 45 s waiting for a module that was not finished. Now DONE is posted only
  by a passing check, `irc wait` ignores messages already on the log, and the
  hook denies `sleep`.

## Why the 25% wall-time target is still missed

The target is 36.0 s (25% of 144.1 s) on 8 modules and 45.3 s (25% of 181.2 s)
on 18 modules. The crew medians are 40.9 s and 54.9 s: 4.9 s and 9.6 s over.
Two causes were measured.

1. The lead `claude -p` process costs about 11-13 s outside the crew: process
   start, plugin load, one model call, teardown. The single arm pays the same
   start and teardown, but it does not pay it on top of a short run.
2. The crew floor is the output generation of the largest module (`ranges.py`,
   about 3.6k output tokens in 22-25 s of API time) plus its dependency chain:
   modules that import `ranges` cannot pass their checks until it does, and the
   CLI module imports the rest.

Not tried yet: splitting `ranges.py` across two workers by function.

## Reproduce

The harness and fixtures lived in the session scratch space; the commands it ran
are the two arms under Method. Each run directory held `result.json` (wall_s,
tokens, cost_usd, passed, tests_touched, and per-process tokens and turns under
`parts`), `lead.log`, one log per worker and `final_pytest.txt`.
